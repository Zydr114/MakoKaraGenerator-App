## 4. 主要发现

1. **SDK2 成本随全曲行数线性增长，而不是随在场行数。** T01 逐帧 Wall 中位从 8 行 31.7 ms 增到 96 行 104.3 ms
   （约 0.8 ms／行，几乎全在 Prepare）；工程首帧从 6 行 2.7 s 增到 120 行 8.2 s；热 seek p95 131 → 218 ms。
   单控制器 WordEmphasis 8 → 96 行只从 8.6 增到 9.0 ms，说明问题在 SDK2 宿主。逐行应用模板时每行每个效果各是一个实例
   （T01 120 行即 600 个），代码中可见的线性来源（未逐项测量归因）：
   - 每实例各自装载一份脚本模块（`FrameEffectHost.Pure.cs` `LoadPure` → `new ScriptModule`）并各建一份纯源索引；
   - 每帧 `Evaluate` 遍历全部实例；
   - 有预设应用时每帧 `StaticStyleProjection.CreateBaseline` 覆盖全部行的字元。
2. **材质与图路径慢一到两个数量级。** CustomInk 148 ms／帧（Material p95 57、Readback p95 78），
   GlassInk 522 ms／帧（Material p95 559、Graph p95 211、Readback p95 311），LineGlitch 42 ms（Readback p95 21）。
   纯控制器样例 Readback p95 只有 2.3～2.5 ms，材质／图样例的读回量和等待明显偏大，
   与 M05 留给 M12 的「零中间读回」未完成项一致。
3. **粒子准备偏重。** CursorTrail 1080p 逐帧 Prepare 中位 22.9 ms（Wall 26.9），VectorTrail／SpriteTrail 约 12 ms；
   逐帧遥测的 Particle 一栏为 0，粒子相关成本都计在 Prepare 内，尚未细分。
4. **作者改动约 1.5 s 才见到新帧。** 其中重新固定输入约 580 ms、新 Worker 出首帧约 950 ms；
   参数改动不改编译产物，但仍走完整的重新固定输入与换 Worker。保存与编译本身都在 50 ms 内。
5. **首帧与 T01 首次远端。** 新工程首帧 1.3～2.7 s（小工程）；T01 首次远端 seek 1.6～2.2 s，而 WordEmphasis 只有 60～70 ms，
   T01 的远端额外成本来自最终锚点补算与粒子准备。
6. **M07 已登记的 ClusterExit 热查询准备 p95 超出仍在**（8.26 ms＞5 ms），方向仍是分层 JIT。
7. **内存与 FD 无持续增长迹象。** 作者 240 次改动 6.5 min，Server 后半斜率 +4.3 MiB/min、FD 平稳，旧 Worker 全部退出；
   短时 seek／导出浸泡都是先升后平。
8. **最终锚点的墙钟保护让结果依赖机器负载。** CursorTrail 冷启动帧要一次补齐粒子寿命窗口内所有出生时刻的
   最终文字锚点，每个时刻都按目标分辨率完整求值一次文字；1440p 下累计超过固定 3 s，GPU 流在 1440p 起播或换分辨率时必然失败
   （24 行也失败，与行数关系不大）。同一内容导出和 720p 能过；按机制推测，换台慢些的机器或负载更高时 720p 也会失败（未实测）。
   次数类预算（时刻、文字调用、未来端点）是确定的，只有这一项随机器变化。
9. **GPU 流每次换源都整份重开 Runtime 输入。** 改动、换分辨率都新开 Worker、重新装载全部实例；
   SDK2 内容下 latest-input 约 6.5 s、分辨率重建约 7 s，应用模板后约 11～30 s 才见到第一帧。与发现 4 是同一机制。

## 5. 门槛候选与优化候选

**2026-11-09 用户决定：**

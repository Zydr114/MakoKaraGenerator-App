## 4. 主要发现

1. **SDK2 成本随全曲行数线性增长，而不是随在场行数。** T01 逐帧 Wall 中位从 8 行 31.7 ms 增到 96 行 104.3 ms
   （约 0.8 ms／行，几乎全在 Prepare）；工程首帧从 6 行 2.7 s 增到 120 行 8.2 s；热 seek p95 131 → 218 ms。
   单控制器 WordEmphasis 8 → 96 行只从 8.6 增到 9.0 ms，说明问题在 SDK2 宿主。逐行应用模板时每行每个效果各是一个实例
   （T01 120 行即 600 个），代码中可见的线性来源（未逐项测量归因）：
   - 每实例各自装载一份脚本模块（`FrameEffectHost.Pure.cs` `LoadPure` → `new ScriptModule`）并各建一份纯源索引；
   - 每帧 `Evaluate` 遍历全部实例；
   - 有预设应用时每帧 `StaticStyleProjection.CreateBaseline` 覆盖全部行的字元。
2. **材质与图路径慢一到两个数量级。** CustomInk 148 ms／帧（Material p95 57、Readback p95 78），
   GlassInk 522 ms／帧（Material p95 559、Graph p95 211、Readback p95 311），LineGlitch 42 ms（Readback p95 21）。
   纯控制器样例 Readback p95 只有 2.3～2.5 ms，材质／图样例的读回量和等待明显偏大，
   与 M05 留给 M12 的「零中间读回」未完成项一致。
3. **粒子准备偏重。** CursorTrail 1080p 逐帧 Prepare 中位 22.9 ms（Wall 26.9），VectorTrail／SpriteTrail 约 12 ms；
   逐帧遥测的 Particle 一栏为 0，粒子相关成本都计在 Prepare 内，尚未细分。
4. **作者改动约 1.5 s 才见到新帧。** 其中重新固定输入约 580 ms、新 Worker 出首帧约 950 ms；
   参数改动不改编译产物，但仍走完整的重新固定输入与换 Worker。保存与编译本身都在 50 ms 内。
5. **首帧与 T01 首次远端。** 新工程首帧 1.3～2.7 s（小工程）；T01 首次远端 seek 1.6～2.2 s，而 WordEmphasis 只有 60～70 ms，
   T01 的远端额外成本来自最终锚点补算与粒子准备。
6. **M07 已登记的 ClusterExit 热查询准备 p95 超出仍在**（8.26 ms＞5 ms），方向仍是分层 JIT。
7. **内存与 FD 无持续增长迹象。** 作者 240 次改动 6.5 min，Server 后半斜率 +4.3 MiB/min、FD 平稳，旧 Worker 全部退出；
   短时 seek／导出浸泡都是先升后平。
8. **最终锚点的墙钟保护让结果依赖机器负载。** CursorTrail 冷启动帧要一次补齐粒子寿命窗口内所有出生时刻的
   最终文字锚点，每个时刻都按目标分辨率完整求值一次文字；1440p 下累计超过固定 3 s，GPU 流在 1440p 起播或换分辨率时必然失败
   （24 行也失败，与行数关系不大）。同一内容导出和 720p 能过；按机制推测，换台慢些的机器或负载更高时 720p 也会失败（未实测）。
   次数类预算（时刻、文字调用、未来端点）是确定的，只有这一项随机器变化。
   **已由 O2 处理**（0.112.47，`bbab181`）：墙钟只作 15 s 挂死保护，T01 24 行 1440p 复测不再失败；72 行未复测。
9. **GPU 流每次换源都整份重开 Runtime 输入。** 改动、换分辨率都新开 Worker、重新装载全部实例；
   SDK2 内容下 latest-input 约 6.5 s、分辨率重建约 7 s，应用模板后约 11～30 s 才见到第一帧。与发现 4 是同一机制。

## 5. 门槛与结构性修复

### 5.0 用户决定

2026-11-09 第一次决定：门槛按原候选 T1～T15 采用；O2 墙钟改为挂死保护（已完成）；做 O1、O3、O4，O5、O6 暂不做。

2026-11-09 第二次决定（取代第一次中的门槛部分）：

### 5.5 材质路径结构排查（2026-11-10，0.112.59，只读，未改代码）

**方法**：条件同 §5.4（720p24、72 行）。计时阶段对 GPU Worker 做 15 s 托管栈采样（`dotnet-trace`，
`dotnet-sampled-thread-time`），另取 15 s 每 100 ms 读一次 amdgpu `gpu_busy_percent` 与 Worker CPU 时间；
再用本地小基准在产品 Vulkan 设备（AMD Radeon 880M，RADV）上测单张表面与背景位图的成本。脚本与结果在
`.local/script-sdk-m12-20261110/`（`trace-o7.sh`、`speedscope-o7.py`、`busy-o7.py`、`SurfaceBench/`、`trace-59/`、`trace-59b/`）。
采样得到的调用次数只是下限（短调用会漏采，连续调用会合并），下文只用时间占比。

| 组 | 采样中 Render p50 | GPU 忙碌 | Worker CPU | 时间去向（占 RenderGpu） |
|---|---|---|---|---|
| 图-直通，纯色 | 6.4 ms | 24.5% | 17% | 场景表面分配（`RasterSceneSurface`）75% |
| 材质-常量色，纯色 | 46 ms | 59.8% | 40% | 场景表面 87%（材质区域捕获 40%、层组装 27%、原色部件 22%）；材质图执行 3% |
| 材质-下层 σ0，棋盘格 | 64 ms | 58.9% | 47% | 场景表面约 90% |
| 材质-背景媒体必需，棋盘格 | 126 ms | 46.8% | 64% | 背景捕获 46%（其中位图绘制 28%）、材质区域捕获 20% |

桌面空闲时 GPU 忙碌约 10%。采样本身使 Render 变慢，绝对值以 §5.4 为准。

小基准（每对象 19 张，与下文一行材质对象的场景表面数相同）：

| 项目 | 720p | 1440p |
|---|---|---|
| 整屏表面「新建＋清屏＋绘制＋快照」，每张同步提交（现状） | 0.136 ms | 0.169 ms |
| 同上，每张异步提交 | 0.064 ms | 0.090 ms |
| 1920×1080 背景位图画满一张表面：可变 `SKBitmap`（现状）／不可变／预上传纹理 | 0.995／0.160／0.162 ms | — |

**发现**
1. **每张场景表面都同步等 GPU**：`RasterSceneSurface`（`SkiaRenderPipeline.SceneSurfaces.cs:65`）分配后无条件
   `FlushAndSubmit`，Vulkan 实现为 `Submit(true)`（`SkiaRenderBackend.cs:352`）。O4 只改了图节点与合成程序；部件捕获、
   材质区域、背景、下层快照、层组装、透明度都走这里。渲染线程一直在忙，而 CPU 只用 40%、GPU 只忙 60%，说明两者在轮流等待、没有重叠。
2. **整屏且数量多**：一行带填充材质的对象（无辉光）经 `RasterSceneSurface` 分配约 19 张整屏表面：
   - 下层快照 1 张；
   - 原色部件 4 张（基础字与注音的描边、阴影）；
   - 材质执行 4 次（基础字与注音的填充，各分未唱、已唱），每次区域与目标原色 2 张，共 8 张；
   - 层组装 5 张（底 1 张，每个原色层 1 张）；
   - 透明度 1 张。

   此外还有不逐张同步的材质图节点、覆盖应用与组合链。图-直通约 10 张。默认最多两行同时可见，切换时多一行。
   单张同步本身只有约 0.14 ms，但材质路径上每张实际耗时是这个的数倍：GPU 被大量整屏像素工作压着，iGPU 又与 CPU 共享内存带宽。
3. **注定为空的部件也照做**：测速歌词没有注音，注音填充材质仍执行未唱、已唱两次；注音的描边、阴影也先整屏捕获，再判空
   （`SkiaRenderPipeline.ImageScene.cs:154`～`:207`）。每行约 8 张表面是空活。
4. **层组装逐层新建表面**：每个没有图历史的层都新建一张整屏表面，再把上一张和本层各画一遍（`SkiaRenderPipeline.ImageScene.Surfaces.cs:43`）。
5. **背景媒体（基线多出约 64 ms 的原因）**：
   - 每次材质执行都调用 `CaptureSceneBackground`，每行 4 次。读下层则每个对象只快照一次并复用。
   - 背景位图是解码一次的可变 `SKBitmap`。`DrawBitmap` 每次都复制像素、重新上传纹理，无法命中纹理缓存（基准 1.0 ms 对 0.16 ms，负载下更高）。
   - 采样中背景捕获每帧约 67 ms，与基线差值吻合；该组 Worker CPU 也从 40% 升到 64%。
6. **重复校验**：每次捕获都调用 `PreparedRenderFrame.ValidateRequest`，其中含全工程 `SourceMaterialCatalog.Collect`，约占渲染时间的 3%～5%。
7. **未发现跨设备读回**：材质与图都用会话设备编译；像素检查关闭时，不会逐张表面读回。

**结论**：材质路径慢是结构性的，原因有三：整屏表面多、逐张同步、空活与重复上传成倍增加。着色器（约 3%）和字形绘制
（约 5%）都不是主因。收紧捕获框（O7）能按面积比减少像素量和预算占用，但消除不了逐张同步与空活，几项需要配合。

| F3 跳过空部件 | 先判空再分配：没有注音的行跳过注音部件与注音材质；样式没有描边或阴影时不捕获 | 每行表面约 19 → 11，材质执行 4 → 2 | 无注音行不执行注音材质（执行次数与预算占用） |
| F4 层组装单遍 | 相邻的无历史层在同一张表面上依次绘制 | 每行少 4 张整屏表面 | 像素逐字节一致，表面计数下降 |
| F5 O7 收紧捕获框 | 按 §5.3 设计实施，所有场景表面与材质／图程序框都改为本行实际区域 | 1440p 不再超预算；像素量按面积比下降 | 1440p 常量色与 CustomInk 帧成功，并读 `ImageSurfaceBudgetSession.Usage` 断言峰值；区域内像素一致 |
| F6 校验每帧一次 | 内部捕获不再重复 `ValidateRequest` | 约 −3%～5% CPU | 不另加回归，现有测试覆盖 |

建议顺序：先做 F1、F2（改动小、相互独立、收益最直接），再做 F5（O7，修 1440p），然后 F3、F4、F6，每步复测后决定是否继续。
备选（暂不做）：同一材质在未唱、已唱两侧合并执行；目标原色按需捕获。两者都涉及语义细节，等前几项复测后再评估。
每步之后重跑 `run-baseline.sh`（纯色、棋盘格两组背景），全部完成后再测 G1 材质组。

**缺背景行为评估**
- **两种状态要分开**：
  - 「透明输出」：透明预览或带 alpha 的导出。现状是背景依赖材质整体退回包内兜底，附 `TransparentBackgroundDependency` 诊断，渲染照常。
  - 「不透明但没有背景媒体」：未设置背景、文件丢失或解码失败、视频在该时刻无帧。现状是必需输入报 `GraphRequiredInputUnavailable`，
    可选输入报 `GraphOptionalInputPolicyPending`，首帧就让整条流失败。
- **渲染时拒绝（即现状）不合理**：一个背景文件丢失，就让整个预览或导出失败，用户连画面都看不到，无从修复。
  背景也可以在套用材质之后再移除或替换。
- **渲染时「不应用材质、画原样」做不到**：一个填充槽只持有一个材质（`FillSpec.cs:3`）。槽里放了包材质，就没有别的原色可画。
  材质没能执行时，能画的只有包声明的兜底外观，所以「不生效」的结果实际就是兜底。
- **编辑时拒绝只能作为提示**：背景之后还能改，文件可能丢失，透明导出要到导出时才选。无论编辑时拦不拦，渲染时都还需要一个不失败的行为。
  若编辑时硬拦，用户就不能先套材质、后加背景，移除背景也得一并拦住，耦合过紧。
- **建议**：
  - 渲染时一律退回兜底，与透明输出走同一路径，诊断写明原因（缺背景媒体），在预览面板与导出前检查中显示；
  - 编辑时（套用此类材质、移除背景）只提示，不阻止。
- **可选输入**：缺失时用工程底色代替。没有背景媒体时，画面实际背景就是底色，与所见一致。
  另一种做法是与必需输入一样退回兜底。需用户选定。

# R4 工程入口与不可变歌词修订接续（0.14.0实施合同）

> 2026-10-04；基线0.13.3。依据已接受合同A的实施合同§7.3／ADR-0071。
> 本批实施歌词闭包和工程入口，脚本包／媒体／分析的完整事务仍按R4接续。

## 1. 数据与授权范围

project.json新增已确认的lyricsFile，值为`data/lyrics/<64位小写SHA-256>.json`。哈希对实际写出的UTF-8歌词JSON字节计算；当前歌词DTO编码／schema保持，不额外保存另一份可读真值。工程schema21→22，程序不兼容MINOR→0.14.0；歌词15、模板3、效果包profile2保持。精确应用版本门禁保持，不迁移旧工程。

不删除旧文件、历史修订或未引用对象。读取只解析入口所指修订，检查规范路径及真实内容hash，缺失／损坏／格式不符报告错误。结构错误不恢复成可保存的空歌词工程；原JSON语义诊断仍通过当前修订解析，不静默修复。

## 2. 写入顺序

1. 当前不可变歌词模型映射为现有DTO，序列化并计算SHA-256。
2. 使用同目录临时文件写出、校验并发布到内容地址；已存在修订必须与本次字节相同，不能覆写。
3. 入口DTO引用该相对路径，其余现有工程字段继续保存。最后原子发布project.json。
4. 任一步失败不让ProjectWorkspace更新saved reference；旧入口及旧修订仍可读取。新未引用修订保留，无自动GC。

本批不声称已完成媒体／效果包／分析资源的整体事务。歌词和入口的发布会消除原先先写入口、再替换lyrics.json造成的混批风险；完整闭包继续沿已批准合同A补齐。

## 3. 备份与复制

AutoSaveStore沿ProjectStore写独立备份目录，因此每份备份含自己的入口及被引用歌词修订。另存为同样从不可变模型写完整歌词，不依赖原工程目录。现有受管媒体仍按原资源收拢规则，本批不改其资源命名或清理策略。

## 4. 验收

当前工程／模板样式／场景／前奏重开继续通过；保存相同歌词复用同一修订，修改歌词得到新修订，原修订不变；入口最后发布失败保留旧工程。缺字段、非法路径、缺失文件、hash不匹配及损坏JSON明确失败，版本门禁在读取歌词前执行。备份／另存为／移动后独立重开及saved reference失败语义验证。旧JSON诊断测试须使用真实当前修订及更新入口，不能因hash错误让原语义断言失去覆盖。

读取根入口一次，版本门禁、DTO解析及lyricsFile选择共用同一份字节；歌词hash校验和JSON解析也共用同一份读取，避免跨修订混读。修订路径严格小写，拒绝data／lyrics／修订文件上的链接；工程根目录本身仍可由用户选定。暂存文件使用唯一名字、刷盘并校验实际字节，发布不覆写已有修订，根入口最后同目录原子替换。

本节先定设计再实施。完成后记录实际结果、版本与日志，同步AGENTS／roadmap／ADR及开发文档。完整R2～R8保持未完成。

新增Core29、Application4项。实际字节hash／没有第二真值、相同修订复用且mtime保持、变更后旧入口可读、已占用损坏修订不覆写、Linux仅禁止入口目录写入时先发布新歌词并保留旧工程、11种非法引用、缺失／修改字节、合法hash下4种坏JSON／schema、版本门禁优先、旧根文件不改、UTF-8标记和注释／尾随逗号、三级链接拒绝、8个并发独立保存；另存为／移动、脱离原目录的备份恢复、失败saved引用和路径保持、损坏修订不替换当前工作区。

工程入口继续以最后原子替换为唯一提交点；本批用同一真实工程快照同时发布歌词修订、音频／背景媒体、音频分析和图／材质效果包。目录搬移后删除原始外部文件，入口仍能从 `data/` 与 `effects/packages/` 重开；从搬移后的闭包另存为会再次发布独立资源，不引用原目录。源材质的包句柄、参数和 profile 与效果实例共用同一包修订校验。

## 8. 0.25.5 后置包发布失败保护

效果包属于工程入口提交前的后置资源。若目标修订目录已存在但内容不符合本次发布，包发布必须报告 `EffectPackageException` 并停止保存；不得把新包路径写入 `project.json`，也不得替换已有入口。旧入口和旧工程必须仍可加载，发布过程中产生的 `*.tmp` 暂存文件必须清理。已经写出的、但没有被入口引用的新内容继续按不可变内容地址保留，不在失败路径上静默删除或回收。

本批只固定包发布失败与旧入口的原子接缝。自动备份、固定 DLL 工作区、模板归档及 R5～R8 仍沿各自合同继续，不因该回归提前视为 R4 总出口完成。

# MakoKaraGenerator 开发文档

- **文档状态**：方案草案 v0.2（已加入开发规划、依赖审计和轮子调研）
- **项目名称**：MakoKaraGenerator
- **项目类型**：基于 C# / Avalonia 的逐字歌词视频制作软件
- **首要平台**：Linux
- **次要平台**：Windows
- **明确不支持**：macOS
- **文档目的**：定义产品范围、核心概念、工程架构、数据格式、渲染流程、脚本系统和分阶段实现计划。

> 本文基于当前已确认的需求编写。文中标记为“建议”的内容是技术方案，不代表已经不可变更的产品决定；标记为“待决策”的内容需要在实现对应模块前确认。

## 1. 产品定位

MakoKaraGenerator 用于替代在 After Effects 等软件中手工制作逐字歌词视频的大量重复劳动。用户可以：

1. 导入歌曲、背景和歌词文件；
2. 导入逐行歌词、逐字歌词，或完全不导入歌词而在软件中创建；
3. 在时间轴、波形和歌词编辑器中完成逐行及逐字打轴；
4. 为整首歌曲、单行歌词或单个字设置文字、布局、样式和动画；
5. 使用内置效果或受信任的 C# 脚本创建复杂的歌词动画；
6. 预览并导出带背景和音轨的成片、透明背景歌词视频以及歌词/时间戳文件。

### 1.1 核心价值

- **时间轴优先**：打轴操作应比在通用合成软件中更直接、更高效。
- **逐字可控**：每个字（更准确地说是 Unicode 文本元素）都拥有独立的时间和视觉状态。
- **所见即所得**：编辑器预览与最终导出必须尽可能使用同一套渲染逻辑。
- **非破坏编辑**：导入的歌词、样式和脚本可以反复修改，不把编辑结果固化为图片。
- **可扩展效果**：基础用户使用内置样式，高级用户使用 C# 脚本扩展动画。
- **可迁移项目**：项目应包含足够的源数据，使其可以在另一台 Linux 或 Windows 计算机上继续编辑。

### 1.2 非目标

首期不以以下能力为目标：

- 完整替代 After Effects 的通用合成、剪辑和特效能力；
- 完整的专业音频编辑、混音或母带处理；
- macOS 支持；
- 在线协作、云端工程管理和账号体系；
- 在不经过用户校正的情况下保证自动歌词识别或逐字对齐绝对准确；
- 在受限沙箱中安全运行来源不明的 C# 脚本。

## 2. 已确认的产品决策

| 项目 | 决策 |
|---|---|
| 平台优先级 | Linux 第一优先，Windows 第二优先，永远不考虑 macOS |
| 歌词来源 | 可以导入逐字格式、逐行格式，也可以完全不导入，在软件内新建歌词 |
| 逐字时间 | 支持导入、手工打轴和后续修正；逐行格式不能伪装成精确逐字时间 |
| 视频输出 | 带背景和音轨的成片；透明背景歌词视频 |
| 时间轴输出 | 支持歌词及逐字时间戳文件导出 |
| 脚本信任模型 | 首期只面向受信任脚本。脚本拥有较高的本机代码权限，不视为安全沙箱 |
| 主要技术栈 | C#、.NET、Avalonia |

### 2.1 推荐的首期默认方案

以下方案用于减少早期反复决策：

- 使用整数微秒保存时间，显示时再转换为毫秒、秒或时间码；
- 使用一个项目原生 JSON 格式作为唯一完整数据源；
- 使用 Avalonia 官方 Skia 渲染集成承载 UI，自定义歌词渲染使用 SkiaSharp，并通过 `SkiaSharp.HarfBuzz` / HarfBuzzSharp 处理复杂文字布局；不要把 `SkiaSharp.Views.Avalonia` 作为核心渲染依赖；
- 使用 FFmpeg 负责音视频封装和编码；首期优先通过 `CliWrap` 管理 FFmpeg 子进程和原始帧管道，`FFMpegCore` 作为可选封装进行技术验证，`FFmpeg.AutoGen` 暂不作为首期依赖；
- 使用 Roslyn 编译 C# 效果；脚本通过稳定的 SDK 接口访问歌词视觉对象，而不是直接依赖应用内部类型，并用可回收的 `AssemblyLoadContext` 支持热重载；
- 预览和最终导出都经过统一的 `RenderPipeline`，只在质量、分辨率和缓存策略上有所区别。

## 3. 用户工作流

### 3.1 从逐字歌词开始

1. 新建项目。
2. 导入音频。
3. 导入原生逐字歌词或其他支持逐字时间的格式。
4. 检查行、字、时间和文本分段。
5. 在波形和时间轴上拖动或微调起止时间。
6. 选择内置样式或创建自定义样式。
7. 在画布中调整字号、位置、颜色、渐变、描边和阴影。
8. 对指定行或字添加局部覆盖和动画。
9. 预览整首歌曲或当前时间范围。
10. 选择输出配置并导出。

### 3.2 从逐行歌词开始

逐行歌词导入后，每一行拥有起止时间，但每个字的时间状态为“缺失”或“未标定”，不能直接显示为已经精确打轴。

用户可以：

- 在行内使用平均分配或按字符权重分配生成“估算时间”；
- 对估算结果整体平移、拉伸或单字修正；
- 播放音频时通过快捷键逐字打点；
- 使用波形和时间轴拖拽调整；
- 最终将状态从“估算”确认成“已校正”。

自动估算可以作为辅助功能，但必须保留来源状态和可撤销性。

### 3.3 无歌词文件

用户可直接：

1. 创建歌词行；
2. 输入或粘贴文本；
3. 通过播放头、快捷键和鼠标完成行级打轴；
4. 将行拆分为字或文本元素；
5. 完成逐字打轴；
6. 继续进行样式编辑和输出。

### 3.4 只制作动画歌词层

用户可以不导入背景视频，使用纯色、图片或透明画布制作歌词层，并输出透明背景视频供其他剪辑软件合成。

- 支持将多个字符合并为一个元素，例如英文单词、标点组合或用户自定义片段。
- 每行保存起始时间和结束时间。
- 每个文本元素保存起始时间和结束时间。
- 导入逐行歌词和至少一种逐字歌词格式。
- 对缺少逐字时间的行提供手工打轴界面。
- 校验重叠、倒序、越界和缺失时间。

- 支持时间吸附、帧对齐和毫秒微调。

  不单独改变字幕输出颜色。
- 至少支持纯色填充、水平渐变、描边、阴影、透明度和基础缩放。
- 支持图片、纯色背景和视频背景中的至少一种组合方式。
- 预览暂停、播放、跳转和循环选区。

#### 输出

- 带背景和音频的常用视频文件。
- 透明背景歌词视频，具体编码格式由平台和编码器能力决定。
- 原生项目歌词/时间戳格式。
- 至少一种逐行歌词格式和一种逐字歌词格式。
- 显示导出进度、剩余时间、错误信息和取消按钮。

## 5. 核心概念和时间模型

### 5.1 时间单位

内部统一使用整数微秒 `long` 保存时间：

```text
1 秒 = 1_000_000 微秒
```

原因：

- 避免 `double` 累积误差；
- 可以精确表达常用音频和视频时间；
- 编辑器可同时显示时间码、毫秒和帧；
- 适合导入不同精度的歌词格式。

视频帧通过帧率换算，不直接把帧号作为唯一时间源：

```text
frameTimeUs = round(frameIndex * 1_000_000 / frameRate)
```

导出时根据编码器要求进行最终帧对齐，并在诊断信息中报告因帧率造成的舍入。

### 5.2 文本元素而不是简单的“字符”

用户看到的“逐字”不一定等于一个 UTF-16 `char`。文本分割应优先按照 Unicode grapheme cluster 处理，以避免：

- emoji 的多个码点被拆开；
- 组合音标脱离基础字符；
- 代理项被错误拆分；
- 变体选择符单独显示。

分割层次建议如下：

1. 用户导入格式提供的显式 token 边界；
2. 用户手工调整的边界；
3. Unicode grapheme cluster；
4. 可选的语言规则，例如按英文单词或标点合并。

每个元素保存原始文本，不改变用户输入。元素可以是一个汉字、一个英文单词、一个 emoji 或多个字符组成的片段。

### 5.3 时间区间

每个歌词行和文本元素使用半开区间：

```text
[startUs, endUs)
```

约束：

- `startUs >= 0`；
- `endUs > startUs`；
- 新架构中元素必须位于所属行的时间区间内；
- 相邻元素可以无缝相接；
- 元素之间允许短暂空隙，用于保留真实停顿；
- 新架构中同一行的已定时元素按文本顺序不得重叠；非法编辑直接拒绝并说明原因。

0.1.0 系列曾报告越行／重叠并保留数据；0.2.0 的编辑入口现在拒绝这类新改动，行内空档画面按 [ADR-0050](../decisions/decisions.md#adr-0050模板工坊歌词行编辑器与程序版本边界) 实现。无效数据不被静默修正。

对于当前时间 `t`，逐字进度为：

```text
progress = clamp((t - startUs) / (endUs - startUs), 0, 1)
```

未来如果需要非线性进度，应由缓动或脚本改变视觉表现，而不直接破坏原始时间数据。

### 5.4 时间状态

每个行和元素都应保存时间来源状态：

- `Missing`：没有时间；
- `Imported`：从文件导入；
- `Estimated`：软件估算；
- `Edited`：用户修改过；
- `Confirmed`：用户明确确认；
- `Invalid`：不满足数据约束。

状态不是装饰信息。导出前可以按状态提示用户哪些字仍然是估算值。

## 6. 原生项目和数据格式

### 6.1 当前工程入口与包结构（0.26.1）

工程使用可读目录，根 `project.json` 为唯一入口：

```text
song.mkgproj/
├── project.json          # 项目入口、程序版本、画布、媒体和轨道
├── data/lyrics/<hash>.json # lyricsFile引用的不可变歌词修订；含源文字／时间／样式
├── effects/packages/<hash>/ # 效果包不可变修订；含manifest.json、C#与全部资源
├── data/media/<hash>.media # 完整音频、背景图片／视频；按内容探测，原名称单独保存
├── data/analysis/<hash>.json # 已接受的完整音频hop修订
├── assets/               # 历史资源目录，保留但不作为当前媒体真值
├── cache/                # 可删除的预览缓存，不属于源数据
└── backups/              # 自动保存备份，可配置保留数量
```

路径应使用相对路径。缓存和备份不参与渲染语义，删除后可以重新生成。

0.25.7 已组合验证模板分享、工程副本及备份搬移后的固定包资源和正式会话。DLL／PDB 仅属本机缓存，按源码／入口／编译器／参考字节身份复用或重建；每个正式会话继续校验当前包资源及原生 ABI，资源变化可复用同一 DLL 而像素必须来自当前修订。缓存损坏、坏源码或原生资源错误阻止当前会话／导出，旧输出保持。验收表见[持久闭包组合验收](../acceptance/scripting-persistent-closure-acceptance.md)／ADR-0118。

### 6.3 数据校验

打开项目、导入歌词和导出前都应运行统一校验器。至少检查：

- schema 版本是否支持；
- ID 是否重复；
- 时间是否为合法整数；
- 行、元素是否存在空文本；
- 元素是否越出所属行；
- 样式引用是否存在；
- 脚本、字体、音频和背景资源是否缺失；
- 输出帧率、画布尺寸和时长是否有效。

校验结果分为：

- **错误**：无法继续导出；
- **警告**：允许继续，但可能产生非预期结果；
- **提示**：不影响输出的建议。

### 6.4 程序版本与项目格式（ADR-0050，0.2.0 已实施）

旧实现用 `project.json` / `lyrics.json` 各自的 `schemaVersion` 和迁移器读取旧文件，这是 ADR-0024/0029 落地时的历史机制。0.2.0 起有意断代：`project.json` 增加必填的程序版本 `applicationVersion`。打开时先比较程序版本；缺失或不一致就提示用户并拒绝打开，原文件保持不变。只有当前版本工程才继续进行两份文件各自的 schema 与数据校验。0.14.0的歌词文件改为入口引用的不可变修订；缺失、路径非法、链接、hash、JSON或schema损坏使加载结构性失败，不能生成可保存空工程。语义错误仍保留原值及诊断。历史迁移器仍编译在 Core 中，但当前 `ProjectStore.Load` 不再走迁移路径。

程序版本在每次完成并交付程序修改时递增；JSON 结构改变时仍提升对应 `schemaVersion`，但不为不受支持的旧工程提供自动迁移。版本号、提示文案和交付规则见 [ADR-0050](../decisions/decisions.md#adr-0050模板工坊歌词行编辑器与程序版本边界) 与 [临时优化方案](../legacy-ui/temporary-style-line-editor-optimization.md#6-断代规则与程序版本)。

## 7. 歌词导入与导出

### 7.1 可扩展接口

建议将格式处理抽象为：

```csharp
public interface ILyricsImporter
{
    string Id { get; }
    bool CanImport(string fileName, ReadOnlySpan<byte> header);
    LyricsDocument Import(Stream input, LyricsImportContext context);
}

public interface ILyricsExporter
{
    string Id { get; }
    LyricsExportReport Export(
        LyricsDocument document,
        Stream output,
        LyricsExportOptions options);
}
```

导入器只负责语法解析和初步映射，不应直接修改 UI 或音频时间轴。

### 7.2 首期格式建议

#### 普通 LRC

- 解析 `[mm:ss.xx]` 等行时间标签；
- 支持同一时间标签对应多行文本；
- 只生成行级时间；
- 逐字时间置为 `Missing`；
- 不把行时间平均分配后伪装为精确数据。

#### 增强型 LRC 或兼容逐字格式

由于不同工具对增强 LRC 的逐字标记并不完全统一，应采用可配置解析策略，并在导入报告中说明识别到的语法。无法识别的标记必须保留在诊断信息中。

#### MakoKara 原生 JSON

- 保存全部行、元素、时间状态、样式引用和局部覆盖；
- 作为无损交换格式；
- 版本化；新架构只接受与当前程序版本一致的工程，不承诺旧版 JSON 自动迁移（ADR-0050）。

#### SRT / WebVTT 等逐行格式

可作为逐行导入/导出格式，但应明确其不携带逐字动画语义。

### 7.3 导入报告

导入完成后显示：

- 识别到的行数和文本元素数；
- 识别到的逐字时间数；
- 估算或缺失的元素数；
- 跳过的行和无法识别的标签；
- 编码、语言和换行符处理结果。

### 7.4 导出损失提示

当目标格式不能表示样式、渐变、脚本动画或逐字时间时，导出器必须先给出损失提示。例如：

- 导出为普通 LRC 会丢失样式和逐字状态；
- 导出为 SRT 会丢失逐字时间；
- 导出为不支持 Alpha 的视频格式会丢失透明背景；
- 导出为逐字格式时，缺失或仅估算的时间应列入报告。

## 8. 编辑器设计

### 8.1 推荐布局

```text
┌─────────────────────────────────────────────────────────────┐
│ 菜单 / 工具栏 / 项目状态 / 播放控制                         │
├───────────────┬───────────────────────────────┬─────────────┤
│ 歌词行列表     │                               │ 属性检查器   │
│ 轨道和资源树   │         画布预览区             │ 样式/动画    │
│               │                               │ 脚本参数     │
├───────────────┴───────────────────────────────┴─────────────┤
│ 波形、播放头、歌词行、逐字块、关键帧、缩放和时间标尺        │
└─────────────────────────────────────────────────────────────┘
```

布局可以随项目推进调整，但歌词列表、画布、属性检查器和时间轴应保持清晰分工。

> **当前实现（0.41.0，ADR-0142）**：首页新建／打开／最近工程／恢复；“歌词与打轴”及“画面与样式”两个常驻任务，共用播放和波形。高级编排、预设制作及效果编辑在主窗口按需打开，草稿切换保留，关闭／换工程／退出明确处理。基础外观即时生效，字段保留非法输入，一次手势一次撤销。完整入口见 [使用路线](../legacy-ui/ui-workspace-guide.md)，历史方案不作为当前入口依据。

> **取色器实现（0.41.0）**：可点色块共用 `ColorPickerPanel`，默认常用色，按需创建上游 `ColorView`；控件采用 Suki 及官方颜色模板，RGBA 通道合同保持。应用主题和视频字体／颜色分开管理。

### 8.2 编辑模式

建议提供明确的模式，避免鼠标操作含义混乱：

1. **选择模式**：选择行、文本元素和视觉图层；
2. **文本模式**：编辑文本、拆分/合并元素；
3. **打轴模式**：播放时设置当前元素起点和终点；
4. **布局模式**：拖动画布中的行或元素；
5. **关键帧模式**：编辑属性随时间变化的关键帧；
6. **脚本预览模式**：查看脚本生成的动态对象和参数。

### 8.3 时间轴交互

必须支持：

- 鼠标拖拽元素左右边界；
- 拖动整个元素而不改变持续时间；
- 多选后整体平移；
- 通过输入框输入精确时间；
- 帧、毫秒、节拍等可选吸附方式；
- 选区循环播放；
- 播放头定位到行起点、行终点、字起点和字终点；
- 从波形峰值或标记点快速定位；
- 0.2.0 起，元素越行或与相邻元素重叠时拒绝该编辑并显示边界；拖动边沿只改所选元素，不联动邻居（ADR-0050）。

### 8.4 推荐快捷键

最终快捷键可以让用户自定义，默认方案如下：

| 快捷键 | 操作 |
|---|---|
| Space | 播放/暂停 |
| J / K / L | 反向、暂停、正向播放 |
| 左右方向键 | 按帧移动播放头 |
| Shift + 左右 | 按较大时间步长移动 |
| I / O | 设置选区起点/终点 |
| Enter | 确认当前编辑 |
| Ctrl/Cmd + Z | 撤销 |
| Ctrl/Cmd + Shift + Z | 重做 |
| S | 拆分当前元素或行 |
| M | 合并选中元素 |
| [ / ] | 设置当前元素起点/终点 |
| F | 聚焦当前对象 |

在 Linux 和 Windows 上应使用各平台习惯的修饰键映射，不要把 macOS 行为纳入设计。

### 8.5 逐字打轴交互

至少提供两种方式：

#### 播放打点

- 播放音频；
- 用户按快捷键记录当前元素的起点或终点；
- 自动跳转到下一个元素；
- 支持回退、重录和量化；
- 结束后自动检查总时长和空隙。

#### 波形拖拽

- 在时间轴上显示每个元素的区间；
- 通过边界拖拽调整；
- 支持多选后批量缩放；
- 支持将最后一个元素的终点对齐到行终点。

### 8.6 字号、样式和位置

属性编辑需要区分三种作用范围：

- **样式预设**：可复用的默认值；
- **行覆盖**：只影响当前歌词行；
- **元素覆盖**：只影响当前字或文本元素。

修改属性时应显示继承来源，例如：

```text
字号：72 px（来自“副歌主样式”）
位置：行覆盖
颜色：元素覆盖
```

用户可以一键“恢复继承”，避免必须手动记住旧值。

元素作用范围只适用于颜色（包括渐变）、描边、阴影和不透明度。字号、字体、纵向位置、对齐
和缩放属于整行排版或整体变换，在元素范围下会被禁用并显示原因。当前选中元素不使用专门的
字幕颜色；它通过时间轴和歌词栏的选中高亮识别。

## 9. 样式系统

> **下一轮改造提案**：渐变停止点/方向/色相、外部描边、字体字重与单字多色、独立样式编辑器、画布位置和多歌词分支的统一规划见 [`docs/style-animation-system-plan.md`](../plans/style-animation-system-plan.md)。本节现有内容描述当前实现基线；提案确认后再按阶段更新数据契约。

### 9.1 样式层级

属性解析建议使用以下优先级，从低到高覆盖：

```text
项目默认值
  -> 样式预设
  -> 轨道覆盖
  -> 歌词行覆盖
  -> 文本元素覆盖
  -> 关键帧
  -> 脚本最终效果
```

脚本不应修改项目源数据中的样式值。脚本产生的是当前帧的视觉结果或临时对象。

#### 覆盖的三态与批量应用（ADR-0044）

覆盖里的 6 个可选颜色（未唱/已唱渐变起止色、描边色、阴影色）有**三种状态**：
**未设置**（继承上层）、**设为颜色**（覆盖上层）、**明确设置为空**（本层关闭该效果，
渲染时回退到最简单的纯色）。旧文件里这些字段的缺失与 `null` 都按"未设置"读取
（`project.json` v10 / `lyrics.json` v6 的迁移做了等价转换；project v11 新增可选完整渐变描述，v12 新增可选描边与方向阴影描述），因此老工程观感不变。

样式的写入不在控件里即时发生：界面先在统一样式工作区的设计稿里编辑，再由
`StyleBatchEditor.Apply` 一次提交到**一个**层级（工程 / 行 / 元素），整批生效或整批不生效，
撤销一步回到应用前。内置样式只读，个人样式的更新只写应用级样式库；只有应用按钮才修改工程。
应用区会在提交前显示明确目标、属性集合和元素不支持项；原歌词栏入口只显示当前对象摘要并打开工作区。

### 9.2 样式属性分类

#### 文字和布局

- 字体族、字体文件、字号、字重、字距、行距；
- 水平对齐、垂直对齐、文本方向；
- 画布锚点、行锚点、元素锚点；
- 自动换行、最大宽度、缩放策略；
- 位置、旋转、缩放、倾斜和基线偏移。

#### 填充

- 单色填充；
- 线性渐变；
- 径向渐变；
- 多色停止点；
- 未唱与已唱两种状态的颜色；
- 当前播放位置由逐字进度边界表达，当前选中元素由时间轴和歌词栏高亮表达；
- 基于逐字进度的渐变偏移。

#### 边缘效果

- 描边宽度、颜色、连接方式；
- 阴影偏移、模糊、透明度；
- 发光半径、颜色和强度；
- 遮罩和裁切区域。

#### 动画

- 透明度；
- 位移、旋转、缩放；
- 渐变进度；
- 描边、发光和阴影强度；
- 关键帧曲线；
- 内置进入、持续和退出动画。

### 9.3 渐变语义

渐变需要明确区分：

1. **空间渐变**：根据像素或字形在画布中的位置取色；
2. **时间渐变**：根据当前逐字进度改变颜色；
3. **混合渐变**：同时受空间位置和演唱进度影响。

最基本的逐字填充应能表达：未唱部分为暗色，当前进度线向前推进，已唱部分为亮色。渐变采样应在渲染器中统一完成，避免预览和导出出现不同结果。

### 9.4 布局策略

逐字高亮不应导致整行文字不断重新排版而跳动。建议采用两阶段处理：

1. 使用完整行文本进行整形和布局，确定每个文本元素的字形边界；
2. 在稳定的布局结果上应用逐字裁切、填充和动画。

当用户明确选择“逐字重新布局”时，才允许每个元素独立布局。

### 9.5 文本渲染兼容性

需要关注：

- 中文、英文、数字、标点混排；
- emoji 和组合字符；
- 字体缺失和字体回退；
- 字体文件许可证和项目打包；
- RTL 文本和复杂脚本的后续支持；
- 不同平台字体名称和字体渲染差异。

建议把文字整形、字形边界计算和实际绘制包装在 `ITextLayoutEngine` 接口后面，避免 UI 直接依赖某个具体库。

## 10. 渲染架构

### 10.1 分层架构

```text
项目数据 / 播放时间
        │
        ▼
时间轴采样器（行、元素、进度、关键帧）
        │
        ▼
文字布局器（字体、字形、边界、基线）
        │
        ▼
样式解析器（继承、覆盖、渐变、状态）
        │
        ▼
脚本效果层（粒子、路径、外部动画对象）
        │
        ▼
场景合成器（背景、歌词层、图层顺序、透明度）
        │
        ▼
渲染后端（预览 / 离线帧 / 视频编码）
```

### 10.2 统一渲染接口

核心渲染器不应知道 Avalonia 控件的存在。建议定义类似以下的接口：

```csharp
public interface IRenderPipeline
{
    RenderFrame Render(RenderRequest request);
}

public sealed record RenderRequest(
    ProjectSnapshot Project,
    long TimeUs,
    RenderQuality Quality,
    RenderTarget Target,
    CancellationToken CancellationToken);
```

`ProjectSnapshot` 应是不可变快照，保证渲染过程中 UI 的修改不会改变当前帧结果。

### 10.3 预览和最终渲染

两者共享：

- 时间采样规则；
- 文本布局；
- 样式解析；
- 脚本 SDK；
- 图层和合成顺序。

两者可以不同的部分：

- 分辨率；
- 抗锯齿和阴影质量；
- 缓存策略；
- 是否跳过不影响预览的高成本效果；
- 编码方式。

如果为了性能跳过效果，必须在界面上明确显示“预览质量”状态，不能让用户误以为最终输出也会缺少该效果。

### 10.4 渲染缓存

缓存键至少应包含：

- 项目数据版本或内容哈希；
- 当前帧时间；
- 画布尺寸和帧率；
- 渲染质量；
- 字体和资源版本；
- 脚本源码及编译参数哈希。

修改歌词时间、样式、资源或脚本后，应使相关缓存失效。缓存放在项目 `cache/` 或用户缓存目录中，不能作为唯一输出来源。

### 10.5 性能目标（建议）

以下是首期可验证的工程目标，不是绝对硬件承诺：

- 1080p 草稿预览在常见 Linux 桌面硬件上尽量接近实时；
- 时间轴拖动时优先保证播放头和歌词反馈，不因完整高质量渲染阻塞 UI；
- 最终渲染在后台线程执行；最终文件发布前可取消，提交阶段仍可查看进度和日志；
- 单帧脚本效果不得无限制阻塞渲染线程；
- 大项目加载采用分阶段加载，先显示基础文本，再加载波形和资源。

具体帧率、内存上限和最大歌词行数应通过基准测试后再固化。

## 11. C# 脚本和动画系统

> **下一轮边界提案**：脚本只调制样式，不负责分支时序、布局槽位、进入/退出动画或新建场景对象。完整的双行动画与翻译分支计划见 [`docs/style-animation-system-plan.md`](../plans/style-animation-system-plan.md)；本节的通用脚本效果接口在脚本阶段开工前按该边界复审。

> **2026-09-30 架构暂停说明**：本节的可变 `IEffectScene` 和“创建场景对象”仍是历史草案。当前合同见 [`scripting-system-architecture-plan.md`](../plans/scripting-system-architecture-plan.md)、[`current-architecture.md`](current-architecture.md)、[`unified-scene-element-plan.md`](../plans/unified-scene-element-plan.md) 和 ADR-0061。已确定主进程内串行、有状态时间线回放、节奏／低频输入、Roslyn 热编译、参数撤销和错误阻止导出。源码进入工程，成功 DLL 进入应用本地数据目录并在退出后保留。脚本只写填充／渐变、描边、阴影、不透明度；统一场景先于脚本实施，当前仍暂停程序开发。

### 11.1 信任模型

首期脚本是**受信任代码**：

- 脚本可以执行普通 C# 代码；
- 脚本可能访问文件、网络、进程或系统 API；
- 编译引用白名单只能用于 API 设计和减少误用，不能被描述为安全沙箱；
- 加载来源不明的脚本前必须显示明确警告；
- 项目打开时不应在用户未确认的情况下静默执行新脚本。

后续如果要支持脚本分享，应另行设计隔离进程、权限声明、签名或操作系统级沙箱，不能把首期信任模式直接宣传为安全执行环境。

### 11.2 脚本 SDK 原则

脚本只依赖稳定的 SDK 程序集，例如：

```text
MakoKaraGenerator.Scripting.Abstractions
MakoKaraGenerator.Rendering.Abstractions
```

脚本不应直接引用：

- Avalonia 控件；
- UI ViewModel；
- 数据库或项目编辑器内部服务；
- 经常变化的私有类；
- 不可序列化的渲染后端对象。

这样可以让脚本在预览和离线导出中使用相同接口，也便于 SDK 版本迁移。

### 11.3 生命周期

推荐的效果生命周期：

```text
编译
  -> 创建实例
  -> OnLoad（读取配置、准备资源）
  -> 每帧 OnFrame（根据时间生成视觉结果）
  -> OnSeek（可选，处理播放头跳转）
  -> OnUnload
```

脚本应尽量把昂贵资源初始化放在 `OnLoad`，而不是每帧加载文件或编译表达式。

### 11.4 历史概念接口（不作为当前合同）

以下为已冻结的早期概念 API，仅保留作历史背景；最终 API 必须按
[`scripting-system-architecture-plan.md`](../plans/scripting-system-architecture-plan.md) 的版本化输入/输出协议重新设计：

```csharp
public interface ILyricEffect
{
    string Id { get; }
    string DisplayName { get; }

    void OnLoad(EffectLoadContext context);
    void OnFrame(EffectFrameContext context, IEffectScene scene);
    void OnUnload();
}

public sealed class EffectFrameContext
{
    public long TimeUs { get; init; }
    public double DeltaSeconds { get; init; }
    public int FrameIndex { get; init; }
    public Size CanvasSize { get; init; }
    public IReadOnlyList<LyricTokenSnapshot> Tokens { get; init; }
    public IDeterministicRandom Random { get; init; }
}
```

`IEffectScene` 至少应支持：

- 读取当前行和文本元素；
- 获取布局后的边界、基线和字形路径；
- 修改当前帧的透明度、变换、填充、描边和遮罩；
- 创建临时粒子、图片、路径和文本对象；
- 设置对象的生命周期、层级和混合模式；
- 注册可显示在属性面板中的公开参数。

### 11.5 逐字动画语义

每个元素向脚本暴露：

```text
Text              原始文本
StartUs / EndUs   时间区间
Progress          0..1 的原始逐字进度
LineProgress      当前行进度
Bounds            稳定布局后的边界
Baseline          基线
Index             行内索引
IsActive          当前是否处于演唱区间
```

脚本可以基于这些值实现：

- 字符弹跳、旋转和缩放；
- 沿路径排列或飞入；
- 字符周围粒子；
- 花瓣、星光、火焰等临时对象；
- 根据进度改变颜色、模糊、发光或透明度；
- 行与行之间的交错动画。

### 11.6 花瓣效果示例思路

花瓣脚本不应修改歌词源文本，而应：

1. 读取每个当前或刚完成元素的进度；
2. 当进度跨过阈值时生成带确定性随机种子的花瓣对象；
3. 根据 `TimeUs` 计算花瓣位置、旋转、透明度和缩放；
4. 把花瓣添加到当前帧的效果层；
5. 在对象生命周期结束后释放它。

随机数必须支持确定性种子，使同一个项目在预览和最终导出中得到一致结果。

### 11.7 脚本参数

脚本可以声明：

- 数值参数；
- 颜色参数；
- 布尔参数；
- 枚举参数；
- 资源参数。

参数元数据应包含名称、默认值、最小值、最大值、步长和分组。项目只保存参数值，不保存由参数即时计算出的临时对象。

### 11.8 脚本错误处理

- 编译错误显示文件、行号、列号和可复制的诊断文本；
- 运行时异常关联到脚本 ID 和当前帧；
- 当前启用脚本在编译、加载、重放或求值失败时，导出任务必须阻止并报告原因；不自动禁用后继续生成成片；
- 脚本不能让 UI 线程崩溃；
- 长时间执行必须支持取消；
- 脚本热重载失败时保留上一份可运行版本。

脚本编译和执行由独立服务合同组织，在主程序进程内按会话串行运行，不依赖 UI 控件；协作取消的限制见脚本方案 §8。

## 12. 音频、背景和视频输出

### 12.1 媒体模型

项目应区分：

- **音频源**：用于播放、波形、时长和最终音轨；
- **背景源**：纯色、图片或视频；
- **歌词视觉层**：可以是不透明或透明；
- **辅助资源**：字体、贴图、脚本资源和效果资源。

音频时间应作为项目主时间线的主要参考。背景视频不足或超出音频时长时，必须有明确的循环、冻结最后一帧、裁切或填充策略。

**0.44.1音频运行时（ADR-0164）**：领域历史只保存音频来源及固定修订。Media层AudioSessionCoordinator拥有播放器、波形和准备请求，按工程会话代次及规范路径／hash／字节数采用结果；普通歌词编辑不重载。导入完整准备后一次命令及交接，历史／打开／恢复先摘除不匹配旧曲再恢复目标；无音频清空，失败保留领域历史并提供重试。恢复不作为导入命令，新工程的已准备播放器只接入一次；UI回传和迟到候选释放有定向证据。EOF与键盘后续F2b，不由本段推定已修复。

> **已实现（2026-09-25，ADR-0041）**：策略为**可切换、默认循环**，另一档是"停在最后一帧"。
> 视频长于输出时长时多余部分不被使用（渲染只走到输出时长），因此不需要单独的"裁切"策略；
> 视频自带音轨被忽略，音频以工程导入的音频为准。

### 12.2 FFmpeg 适配层

建议把 FFmpeg 调用封装为 `IMediaEncoder` / `IMediaProbe`：

- 探测媒体时长、分辨率、帧率、音频轨道；
- 启动视频编码进程；
- 写入渲染帧；
- 合并或复制音频；
- 读取进度和错误；
- 取消并清理临时文件。

不要让 ViewModel 直接拼接 FFmpeg 命令行。所有命令参数都应由强类型输出配置生成，并在日志中记录已执行的安全摘要。

FFmpeg 的许可证、编解码器可用性和打包方式需要在发布前单独确认。Linux 和 Windows 的编码器能力不能假设完全相同。

### 12.3 输出配置建议

| 输出类别 | 作用 | 首期策略 |
|---|---|---|
| 不透明成片 | 背景 + 歌词 + 音频 | 提供常用 MP4 配置，编码器可配置 |
| 透明歌词视频 | 歌词层带 Alpha，供后期合成 | 根据实际编码器提供支持的格式，并在界面标明透明通道 |
| 原生歌词时间轴 | 完整保存逐行、逐字时间和状态 | 使用 MakoKara 原生 JSON |
| 兼容歌词文件 | 与其他歌词工具交换 | LRC、逐字扩展格式或其他插件格式 |

透明输出不是所有容器和编码器都支持。输出配置必须在导出前验证 Alpha 能力，不能仅根据文件扩展名判断成功。

### 12.4 导出流程

```text
校验项目
  -> 固定项目快照
  -> 探测音频和背景
  -> 编译/加载脚本
  -> 创建编码器
  -> 按帧采样统一渲染管线
  -> 写入视频帧
  -> 合并音频
  -> 完成暂存封装并交接产物所有权
  -> 探测暂存文件并形成最终路径报告
  -> 释放渲染和编码会话
  -> 最后取消检查
  -> 同目录发布最终文件
  -> 返回成功报告
```

0.44.0按[ADR-0163](../decisions/decisions.md#adr-0163导出暂存所有权与最终发布事务04402026-10-08)修复验证阶段取消覆盖旧输出的问题。编码完成只返回调用方拥有的`VideoEncodingArtifact`，不是最终路径已改变；导出事务唯一负责发布及清理。验证仍可取消，`Committing`仅执行短暂发布，发布成功后的取消或完成通知异常不改写成功。禁止覆盖在实际发布时受检，发布失败保留原目标；探测告警严重性及效果Error门禁保持。实际测试与完成边界见[修复验收](../acceptance/code-review-remediation-acceptance.md)。

导出报告至少包含：

- 输出路径、分辨率、帧率和时长；
- 实际编码器和容器；
- 音视频时长差；
- 丢帧、渲染失败和缺失资源；
- 脚本警告；
- 是否存在估算或未确认的逐字时间。

## 14. Linux 和 Windows 平台策略

### 14.1 Linux 第一优先

首期开发和验证优先覆盖：

- Linux x64；
- 常见 Wayland 桌面环境；
- X11 兼容运行；
- 系统字体目录和用户字体目录；
- 系统或应用自带的 FFmpeg 适配；
- AppImage、压缩包或 Flatpak 中的一种发布方式。

Avalonia、Skia、FFmpeg、字体和文件选择器在不同 Linux 发行版中可能存在差异。构建和发布时要把运行时依赖列为诊断项，而不是假设用户环境一致。

### 14.2 Windows 第二优先

Windows 阶段重点验证：

- 路径、盘符和 Unicode 文件名；
- 字体发现和回退；
- FFmpeg 子进程启动与取消；
- 高 DPI 缩放；
- 视频编码器和透明输出；
- 项目在 Linux 和 Windows 间的相对路径迁移。

### 14.3 不考虑 macOS

项目文档、构建脚本、快捷键映射和测试矩阵不需要为 macOS 保留专门兼容层。跨平台代码仍应避免无必要的平台硬编码，但不以 macOS 行为作为验收目标。

## 15. 测试策略

### 15.1 单元测试

优先覆盖：

- 微秒、毫秒、帧之间的换算；
- 时间区间约束；
- grapheme cluster 分割；
- 歌词导入和导出；
- 行与元素拆分、合并；
- 样式继承和覆盖优先级；
- 渐变采样和进度计算；
- 关键帧插值；
- schema 迁移和项目校验；
- 脚本参数序列化。

### 15.2 渲染金样测试

对固定项目和固定时间生成图片，与基准图片比较：

- 普通文字；
- 中文、英文、数字和 emoji；
- 描边、阴影和渐变；
- 行级和逐字进度；
- 关键帧；
- 脚本粒子和确定性随机数；
- 透明背景。

金样测试需要固定字体、渲染后端版本和画布参数，否则应把差异分类为环境差异而不是直接判定功能失败。

### 15.3 集成测试

- 项目保存后重新打开，数据不丢失；
- 导入歌词后修改、撤销、重做；
- 从普通 LRC 到逐字打轴再导出；
- 预览帧和最终渲染帧使用相同输入时结果一致；
- 音频、背景视频和透明歌词正确封装；
- FFmpeg 不存在、版本不兼容或编码器缺失时给出可理解提示；
- 脚本编译错误和运行时异常不会导致 UI 崩溃。

### 15.4 性能测试

建立可重复的基准项目，测量：

- 项目打开耗时；
- 波形生成耗时；
- 预览帧耗时；
- 单帧脚本耗时；
- 最终渲染吞吐量；
- 内存峰值；
- 缓存命中率。

不要在没有基准数据的情况下过早写死“最大歌词行数”或“最大粒子数”。

## 17. MVP 验收标准

MVP 可以被视为完成，需要满足：

1. Linux 上可以创建、保存和重新打开项目；
2. 可以导入普通逐行歌词，也可以不导入歌词而手工输入；
3. 可以把歌词拆分为逐字或逐文本元素；
4. 可以通过时间轴、波形和快捷键编辑行级、元素级时间；
5. 普通 LRC 导入后明确标记逐字时间缺失或估算状态；
6. 预览中可以看到逐字进度；
7. 可以编辑字号、样式、位置、颜色和基本渐变；
8. 预览与最终导出的逐字进度使用同一套时间语义；
9. 可以输出带音频和背景的成片；
10. 在可用编码器支持下可以输出透明歌词视频；
11. 可以导出原生逐字时间轴文件；
12. 导出失败时能指出缺失资源、非法时间、脚本/编码器或格式问题；
13. 关键编辑操作支持撤销和重做；
14. 项目中的相对路径和资源状态可以在 Linux 环境中稳定恢复。

## 19. 设计底线

开发过程中应始终遵守以下原则：

- 不把逐行时间平均分配后标记为精确逐字时间；
- 不让 UI 控件成为渲染器的依赖；
- 不让预览使用一套、导出使用另一套时间算法；
- 不把脚本生成的临时视觉对象写回歌词源数据；
- 不将缓存当作项目的唯一数据源；
- 不在未提示用户的情况下执行新加入项目的受信任脚本；
- 不把“允许执行本机代码”的脚本模型描述为安全沙箱；
- 不因支持 Windows 而牺牲 Linux 首要平台的可测试性；
- 不为 macOS 添加产品验收目标；
- 所有可能造成数据丢失的操作都必须可撤销或先备份。

## 21. 现有轮子调研与推荐选型

本节记录本次调研得到的可复用组件，以及它们在 MakoKaraGenerator 中的边界。版本号不在设计文档中写死，实际版本应在项目建立后通过中央包管理和可复现构建锁定。

### 21.1 推荐组件

| 领域 | 首选组件 | 使用方式 | 结论 |
|---|---|---|---|
| 桌面 UI | `Avalonia`／`Avalonia.Desktop` 12.1.3、`SukiUI` 7.0.1 原生控件及窗口 | 编辑器窗口、控件和主题；自有样式仅布局／绘图区 | 当前采用；外观与任务口径见 ADR-0142 |
| UI/自定义绘制 | `Avalonia.Skia`、`ICustomDrawOperation`、`ISkiaSharpApiLeaseFeature` | 将渲染器接入 Avalonia 画布 | 首期采用 |
| 2D 渲染 | `SkiaSharp` | 文字、路径、渐变、粒子和离屏帧 | 首期采用 |
| 文字整形 | `SkiaSharp.HarfBuzz` / `HarfBuzzSharp` | 获取正确的 glyph、advance、cluster 和字形位置 | 首期采用 |
| FFmpeg 进程 | `CliWrap` | 异步启动、取消、标准输入输出和错误流 | 首期优先采用 |
| FFmpeg 高级封装 | `FFMpegCore` | 媒体探测、原始帧管道和编码技术验证 | 可选 |
| FFmpeg 原生绑定 | `FFmpeg.AutoGen` | 需要直接操作 FFmpeg API 时使用 | 后续再评估 |
| C# 编译 | `Microsoft.CodeAnalysis.CSharp` / `Microsoft.CodeAnalysis.CSharp.Scripting` | 编译效果脚本和可选的脚本式入口 | P2 采用 |
| 插件热重载 | .NET `AssemblyLoadContext`、`AssemblyDependencyResolver` | 每个脚本版本独立加载和卸载 | P2 采用 |
| 音频分析 | FFmpeg 解码 PCM + 自研峰值聚合；可选 `NWaves` | 波形、音量、频谱和后续节拍分析 | 首期不引入音频设备库 |

### 21.2 选型边界

#### Avalonia 与 SkiaSharp

Avalonia 本身使用 Skia 绘制控件。歌词画布不应依赖普通控件逐字堆叠，而应使用自定义绘制操作，把 `RenderPipeline` 的结果交给 Avalonia 显示。

`SkiaSharp.Views.Avalonia` 在调研中表现为旧式/不应作为当前核心集成的路径。项目应优先使用 Avalonia 官方 Skia 集成和自定义渲染 API，避免出现两套 Skia 视图封装和 native asset 版本冲突。

SkiaSharp、HarfBuzzSharp 和 Avalonia 的 Skia native asset 需要集中管理版本，不能分别盲目升级。

#### FFmpeg、CliWrap 与 FFMpegCore

MVP 默认直接调用 FFmpeg：

```text
SkiaSharp 离屏 RGBA 帧 -> stdin -> FFmpeg -> 视频文件
```

`CliWrap` 负责进程生命周期、取消和管道；应用自己控制 FFmpeg 参数，以便明确处理 Alpha、像素格式、音轨和进度。`FFMpegCore` 可以在技术验证阶段比较其 raw frame pipe 是否减少实现成本，但不能让 ViewModel 直接依赖它。

`FFmpeg.AutoGen` 能提供更底层的控制，但会引入 unsafe 代码、native binding 和更高的跨平台维护成本，因此不进入首个垂直闭环。

#### C# 脚本

效果脚本以普通 C# 类型或脚本入口为主，使用 Roslyn 编译为程序集，再通过可回收 `AssemblyLoadContext` 热加载。每个预览／导出会话在主进程内使用专用串行调度器，允许保留可重建的时间线历史和音频特征状态；脚本 API 不直接依赖 UI 内部对象。`CSharp.Scripting` 可用于轻量表达式或技术验证，最终 SDK 仍需固定版本化 DTO 和事件合同。

`AssemblyLoadContext` 只提供依赖加载和卸载能力，不提供安全隔离。受信任脚本模型必须继续保留安全警告。

#### 音频与歌词解析

Linux 是第一目标，因此首期不把 NAudio 作为音频主链路。波形可以由 FFmpeg 转 PCM 后在 MakoKaraGenerator 内计算，播放也应通过统一的媒体适配层抽象。

普通 LRC 语法足够简单，但增强 LRC 的逐字标记并不统一。本次搜索未得到稳定、可核实且适合本项目的第三方解析器；后续应先实现带诊断和保留未知标签能力的自有解析器，再按格式逐个加入适配器，而不是锁定一个未经验证的 NuGet 包。

## 23. 依赖落地策略

1. 使用 `Directory.Packages.props` 集中管理包版本；
2. 将 Avalonia、SkiaSharp 和 HarfBuzz 的版本作为一组验证，不独立升级；

5. 第三方包引入前记录许可证、native asset、Linux/Windows 支持和维护状态；
6. 不把本机全局 NuGet 缓存或系统 FFmpeg 版本写入项目语义；
7. CI 至少执行 Linux 构建、单元测试和无窗口渲染测试，Windows 构建随后加入。

## 25. 独立行位置与布局编辑（ADR-0053）

`LyricLine.Placement` 可为空；对象保存归一化 `Position(X,Y)`、`Anchor`、`RotationDegrees`、`Scale`。
歌词文件的 `placement` 对应 `x/y/anchor/rotationDegrees/scale`。坐标须在 0–1，角度有限，缩放为正；
非法值报告诊断，不改写用户数值。模板只承载样式，不承载行位置。

位置为空时，生效样式的水平对齐和纵向比例解析排版默认；显式位置覆盖这两项排版默认。
锚点按实际字形边界求得；缩放为样式基础缩放乘位置缩放，旋转与缩放围绕锚点。
`ILineGeometryProvider` 提供同一份几何给渲染、编辑边界与命中；控件只换算画布像素与界面像素。

布局模式显示当前行静态试样（包括未定时行），暂停播放并暂收起主时间轴；退出恢复正常时间预览。
静态试样通过独立请求字段指定，不改歌词时间，不复用正常时间帧缓存。导出不请求编辑试样或辅助线。
拖动只换临时快照，松开后一次提交；取消、切行或工程变化丢弃临时快照。
批量先检查稳定行 ID 与源工程、显示结果再确认；无变化不写入历史，失效结果整批拒绝。
分支默认和布局槽位优先级随分支容器接入；实施状态只维护于 `roadmap.md` §18.9。


## 26. 歌词分支、场景与注音（ADR-0054）

0.3.0 的歌词根对象保存 `schemaVersion/primaryBranchId/branches`；分支包含行、语言、时间／动画策略、
样式覆盖、默认位置、安全区、最大宽度和双行配置。`Lines/Language` 是主分支便捷访问，磁盘不存平行副本。
稳定 `primaryLineId` 关联主行，不以行下标配对；关联失效诊断，不静默重关联。
分支编辑投影只复用单分支行操作，实际主分支 ID 在提交结果中恢复，渲染和保存从不使用编辑投影。

可见性与双行编排由 `LyricSceneSampler` 从时刻重建；逐字状态来自 `LyricSampler.SampleLine`。
下一行可提前进入槽位，逐字进度仍只来自自己的时间。进入／保持／退出通道不写回样式或时间；
短行压缩动画阶段，旧行保留与槽位冲突按配置处理。翻译默认静态；可选整体动画跟随不会复制逐字高亮。
同一分支的静态关联行先测量再在安全区分行，用户显式位置优先。

行内 `rubyAnnotations` 保存基础字 ID、文本、语言、比例、间距与对齐，没有独立时间轴。
基础行只整形一次；注音单独整形、联合占用先测量后定位，基础字的逐字边界保持稳定。
正常预览与导出使用同一场景和布局；编辑试样／辅助线不进入成片。
当前格式与版本边界、实施证据和未实现的高级编排见样式计划 §15、roadmap §18.10。

0.3.1 起，双行模式由槽位拥有主歌词位置；逐行位置数据保留但暂不参与动态渲染，布局编辑器在该模式下禁用逐行位置写入。关闭双行后恢复原行位置。0.3.2 起，分支可选用 `DualLineGroupTransform` 在槽位外层统一平移、旋转和缩放；普通模式不消费该变换，槽位之间的相对关系由同一个整体变换保持。


### 现行展示合同补充（0.6.0，ADR-0062）

上文 0.3.x 的专用双行整体变换与逐行位置所有权属于历史实现。当前工程 v18 的 lyricPresentation 独占容器位置、固定参考尺寸、内部默认／逐行位置、槽位、分支动画策略和行进入覆盖；歌词 v15 不再保存展示字段。普通与双行共用分支 Group 外层位置，只有内部布局策略变化。静态试样、命中与时间渲染共用 SceneFrame 测量；试样不带时间动画。当前字段与代码职责见 [当前架构盘点](current-architecture.md)，验收见 roadmap §18.17。不转换旧工程。

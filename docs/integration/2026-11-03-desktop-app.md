# 2026-11-03 桌面版整合：一条命令启动，默认走 GPU 共享纹理

界面改版（台前幕后）七批 2026-11-03 通过用户验收后，用户要求“先整合为可实际启动、能够正确低拷贝 GPU 预览的 Electron 应用，完成后启动应用”。本次只做功能整合，不改持续 GPU 流协议，也不改浏览器入口的行为；性能沿用现状，P3 门槛另作任务。

## 用户决定（2026-11-03）

| 问题 | 决定 |
| --- | --- |
| 启动形式 | 仓库内一条命令：`pnpm desktop` 检查构建是否过期，过期就重建，再打开窗口；仍从终端启动，不做安装包 |
| 默认预览 | GPU 可用就走共享纹理：桌面版里渲染设备为“跟随后端默认”（检测到 GPU 可用）或“GPU”时，编排页、外观页的成片预览走 GPU 连续预览；只有明确选 CPU 时退回 PNG 静态预览。浏览器不变 |
| 完成标准 | 功能正确：真实工程里 GPU 预览出帧；播放、暂停、拖动、编辑都会刷新；切页和关窗正常；每帧没有 CPU 像素回读。不测性能 |

## 改动

- `dc5e0ce`：`usesGpuStream` 按上面的规则决定成片预览走哪条路；GPU 预览标题栏的“GPU 预览规格”改用新控件。
- `fac2c8d`：
  - `pnpm desktop` 启动前按源码内容哈希（不看修改时间）检查三样东西：Web 构建（`.local/web-build.json`）、后端发布（`deployment.json` 的 `sourceInputs`，规则同 `host.py`）、GPU 预览原生库（`gpu-preview-manifest.json`）。后端或原生源码有改动时整套重建，只有前端改动时只重建 Web。
  - 桌面版固定 5180 端口，页面的本机偏好跨次保留；启动时按 PID 清掉已退出进程留下的私有启动文件。
  - 窗口去掉 Electron 默认菜单，按工作区收小，最小 1024×640，带应用图标，画好后再显示。
  - 关窗前在页面里派发 `beforeunload`：工程、样式库模板或作者草稿未保存时弹窗确认，确认后才排空 GPU 消费者、停掉 Web 与后端。
- 冒烟与验收脚本：新增 `pnpm smoke:desktop`；`smoke:browser`、`smoke:layout`、P3 与背景验收脚本里的旧 mdui 选择器改用 `frontend/scripts/ui-query.mjs`。

## 已知问题

### K1：暂停或刚接上流时的那一帧可能被渲染端丢掉，画面停在旧帧或一直“准备中”

用户 2026-11-03 在检查会话里看到：外观页 GPU 预览一直显示“准备中”（约 1 分钟），点播放后立刻正常出帧，流畅度符合预期。用户决定：能正常使用就先搁置，这次只验证前端修改后的回归。

现象与证据（未提交的本机证据在 `.local/desktop-check-bug/` 和 `.local/gpu-preview-p3/2026-11-02T17-52-40.559Z/`）：

- 检查会话里所有接上的流都在 90～130 ms 内产出首帧，渲染端门控累计丢了 2 帧，最后一次原因是 `waitingBarrier`。
- P3 调试运行里，暂停后后端 9.5 ms 就产出了对应暂停控制（控制序号 17）的那一帧，但它以 `waitingBarrier` 被渲染端丢掉（`drawn:false`）。之后门控已经放开（hard 17、barrier 17），可是暂停状态下后端不会再出新帧，画面就一直停在旧帧。

原因：`desktop/gpu-preview/preload.cjs` 在播放状态变化（暂停、拖动、刚接上流）时先关上门控，要等两件事都到了才放开：`mako-gpu:playback` 的 IPC 回复带回控制序号，以及主进程转来的 `mako-gpu:barrier`。共享纹理帧和这两条 IPC 消息不保证先后，帧先到就会被丢掉。播放时后续帧会补上，看不出来；暂停时那一帧就是最后一帧，丢了就不再刷新。这是 P1/P2 时期渲染端门控就有的竞态，不是这次界面改版或桌面整合引入的。

暂时的绕法：点一下播放，或再拖一下播放头。修复要改持续预览的消费端门控（例如门控放开时若刚丢过当前控制的帧，就请后端按当前状态重出一帧），按约定需要单独审查，留作后续任务。

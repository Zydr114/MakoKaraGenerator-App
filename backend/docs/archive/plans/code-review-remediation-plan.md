## 3. 修复边界与共同规则

1. **不改变已接受的制作模型。** 三个同级任务、工坊制作参数、画面区应用固定组合预设、一个对象一个应用、一次手势一次撤销继续有效。SDK 高级能力、父捕获／组图、复杂映射、跨输出计划和兼容旧工程不属于本次修复。
2. **状态只有一个明确来源。** 工程历史保存领域数据；播放器、作者草稿、库快照和输出事务各自拥有运行状态，通过稳定身份协调。不能把播放器或可变控件放入 Project，也不能以当前控件选择代替异步请求的发起目标。
3. **提交前可取消，提交后如实报告。** 文件发布、库索引发布、草稿写入各有单一提交点。资源准备不等于提交；迟到取消不能把已提交操作报告为未发生。失败时保留原内容和可恢复草稿。
4. **保留现有安全门禁。** 不降低闭包 hash／链接／版本校验，不取消每份备份的独立闭包，不用旧 DLL 回退编译失败，不用吞掉诊断或修改 120Hz 网格获得性能收益。
5. **按行为拆提交。** 每个提交包含相应修复、回归和文档；重构与行为修复尽量分开。复现测试先在旧行为上确认失败，修复后通过；不把故意失败的测试提交到 main。按 [AGENTS.md](../history/AGENTS-20261029-history.md) 做对应变异检查。
6. **保留当前格式边界。** 计划基线是工程／歌词／模板 **28／16／6**、脚本配置 **1**、包 profile **2**。以下方案预计不需修改持久化 schema；若实施改变公共宿主协议或程序集，按现有版本规则判断程序 MINOR，并同步 ADR，不提前指定一个虚假的“已发布版本”。

## 4. F1：导出提交边界（R01）

入口：[FfmpegMediaEncoder](../../../src/MakoKaraGenerator.Export/FfmpegMediaEncoder.cs)、[VideoExporter](../../../src/MakoKaraGenerator.Export/VideoExporter.cs)、[编码会话接口](../../../src/MakoKaraGenerator.Export/IMediaEncoder.cs)。

**选择的方案：编码器产出暂存文件，由导出事务负责最终发布。** 目前编码器 `CompleteAsync` 先覆盖最终路径，上层才执行可取消的报告探测。修复后的顺序为：

`渲染／编码 → 完成暂存文件 → 探测暂存文件并形成报告 → 释放可能失败的运行资源 → 最后一次取消检查 → 发布最终文件 → 返回成功`

- 为编码会话提供明确的暂存产物结果和所有权转移。编码完成不再暗含“用户最终路径已更新”；导出事务唯一负责提交或清理，暂存位置与目标在同一文件系统。
- 报告构造区分“探测的物理暂存路径”和“向用户报告的最终路径”，报告不暴露临时路径。保留当前探测告警的严重性规则，不能顺带把所有 probe 警告改成导出失败。
- 进入提交后只执行短暂发布，不再运行可取消的探测或脚本工作。发布成功后的状态通知、取消到达及非关键清理不得把结果改写成“取消、旧文件保持”。发布失败保留旧文件，返回真实失败。
- `Overwrite=false` 在实际提交时仍须保证不覆盖并发出现的目标文件。取消、渲染失败、编码失败及提交前释放失败清理自己的暂存文件，不能清理用户原文件。
- UI 的取消可用状态与事务阶段一致；“正在完成”对应实际短提交阶段，不用提前禁用整个验证阶段掩盖问题。

**验收：** 用真实 FFmpeg 和含可识别内容的旧文件，分别在渲染、编码完成、验证开始、验证中和最后提交前取消，断言旧文件逐字节保持、无自有暂存残留。提交后注入取消必须返回已完成及正确新产物。覆盖 MP4／透明输出、无旧文件、禁止覆盖、发布失败和资源释放失败；保留现有作者 Error 保护旧输出的测试。

## 5. F2：媒体会话与播放命令（R02／R05／R06）

入口：[AudioLoading](../../../samples/TechnicalSpike.App/ViewModels/EditorViewModel.AudioLoading.cs)、[Commands](../../../samples/TechnicalSpike.App/ViewModels/EditorViewModel.Commands.cs)、[Playback](../../../samples/TechnicalSpike.App/ViewModels/EditorViewModel.Playback.cs)、[工程打开](../../../samples/TechnicalSpike.App/Views/MainWindow.Project.cs)、[键盘路由](../../../samples/TechnicalSpike.App/Views/MainWindow.Keyboard.cs)。

### F2a：音频身份统一驱动运行时

抽出可独立测试的媒体会话协调器，拥有播放器、波形、时长、状态和加载请求。身份至少包含工程会话代次及实际音频修订／来源；普通歌词编辑不应因 Project 引用变化而反复重载音频。

| 场景 | 领域与运行时行为 |
| --- | --- |
| 导入新音频 | 先准备候选播放器和波形，准备失败保持原工程和可用播放器；成功后一次命令更新模型并安装已准备候选 |
| 撤销／重做改变音频 | 历史先确定目标音频；立即停止并摘除不匹配的运行时，再异步恢复目标，显示加载状态 |
| 打开／恢复另一工程 | 增加会话代次，取消旧请求、取消事件订阅，清空旧音频展示；只接受新工程对应结果 |
| 目标没有音频 | 进入 Empty，播放器、波形、播放标记及音频时长均清空 |
| 撤销／打开后的恢复失败 | 保留目标工程与历史，运行时为 Unavailable，显示原因及重试入口；不悄悄播放旧曲或反向撤销模型 |
| 迟到准备完成 | 对身份及请求代次复核，不匹配则释放候选，不能更改模型、历史或当前播放器 |

工程命令继续是纯数据命令。协调器不能为历史中的每个版本常驻播放器，也不能靠某个导入按钮手动补齐状态。状态回传在 UI 线程更新，后台事件带会话身份，重复关闭和失败清理幂等。播放头遵循现有导入／恢复规则，在目标运行时安装后按有效时长夹取；恢复过程中不读取旧播放器位置。

**验收：** A→B→撤销→重做同时断言实际播放源、波形、时长和模型；覆盖无音频工程、缺失文件、准备失败、快速换工程、撤销时仍在加载、过期播放器事件及重复释放。继续覆盖现有“新建必须音频和主歌词都准备成功”及迟到演示音频保护。

### F2b：结束事件与 J／K／L／Space

由 F2a 会话订阅 `PlaybackEnded`，并通过实际后端状态校正播放标记。结束事件、轮询和按钮共用状态转换，旧播放器的回调不能暂停新播放器。

建议交互：无循环 EOF 时停在末尾并显示已停止；再次按播放／L／Space 从 0 开始。有有效循环时从循环入点继续，防止末尾事件把刚重启的循环误设为停止。J 保留已裁决的后退并正放、Shift 微调及允许回到循环入点之前的规则；不把 J 改成倒放。K 始终执行幂等暂停，Space 才执行切换。

**验收：** 播放／暂停／EOF 三种起点的真实窗口路由；按键重复、循环出点等于文件末尾、J 后的恢复、换源后迟到 EOF。按钮外观与后端状态一致，文本编辑和输入法焦点不被全局键盘处理误夺取。物理键盘与输入法验收单列，Headless 通过不代替人工结论。

## 6. F3：库仓储与并发提交（R03，支撑 R13／A03）

入口：[TemplateWorkshopViewModel](../../../samples/TechnicalSpike.App/ViewModels/TemplateWorkshopViewModel.cs)、[模板传输](../../../samples/TechnicalSpike.App/ViewModels/TemplateWorkshopViewModel.Transfer.cs)、[现有传输合同](../../scripting-r7-template-transfer-contract.md)。

**选择严格冲突检测，不做自动覆盖或无提示合并。** 增加应用层库仓储，普通保存、删除、导入共享 `读取快照＋修订 → 提交变更` 协议，底层沿用现有闭包存储。

- 包等不可变资源可提前准备；同一路径的最终提交必须取得跨进程协作锁，在锁内重新读取并校验 expected revision，再按“资源先发布、索引最后发布”完成写入。锁由操作系统持有并随进程退出释放；不要用无法判断是否存活的遗留标记文件充当锁。
- 本应用的所有写入入口参加同一协议，既有 `.mktpl` 的检查也要并入锁内。独立脚本配置库若共用相同持久化写入机制，一并接入该提交原语，保持各自 schema 和冲突语义。
- 冲突时保留作者草稿和非法输入，显示库已变化；用户可以刷新后重新处理，或明确保存为具有新 ID 的副本。刷新不等于丢弃草稿，保存副本也必须针对重新读取的修订提交。
- 协作锁保证参加协议的应用实例互斥；不能宣称能够锁住任意外部编辑器。对检测到的外部变化拒绝旧修订写入，文档写清该边界。
- 成功返回新快照和修订并发出一次库变化通知。索引提交之后迟到取消仍报告成功；失败不发成功通知。

这扩展了原模板传输合同中“没有跨进程锁”的边界，实施时补 ADR 和合同，不改变模板 archive 的重复 ID、闭包校验与原子批量导入规则。

**验收：** 两个真实进程从同一空库启动，先后／同时新增、编辑同一模板、删除与导入竞争，保证没有静默丢失更新；测试锁等待取消、持锁进程退出、资源写失败、索引发布失败及外部修改。单进程双 VM 是快速回归，不能替代跨进程验证。

## 7. F4：作者草稿、异步目标和任务命令（R04／R08／R07）

### F4a：原始输入与合法预览分离

## 10. F7：脚本历史与诊断成本（R09／R10）

入口：[FrameSession](../../../src/MakoKaraGenerator.Scripting/Execution/FrameSession.cs)、[TimelineHistory](../../../src/MakoKaraGenerator.Scripting.Abstractions/TimelineHistory.cs)、[FrameEffectHost](../../../src/MakoKaraGenerator.Scripting/Execution/FrameEffectHost.cs)、[PreparedRenderFrame](../../../src/MakoKaraGenerator.Rendering.Abstractions/PreparedRenderFrame.cs)。

两个优化分别提交，先保留修复前可复测的基准。固定空脚本／合法 50Hz 音频事件与每 Evaluate 报告一次 Warning 的脚本，测 10／30／180 秒的累计分配、峰值托管内存、推进时间、记录校验数和实际诊断访问数；隔离运行并预热，多次取中位值。原审查 10／20／40 秒的历史累计分配约 71／207／662 MB，仅是机制观测，不能作为目标机器的硬性性能线。

### F7a：一次验证、不可变前缀

每个重放代次建立一次经过校验的固定事件表，事件带该代次的 ReplayReason。History 持有只读表、可见记录数和当前时刻；宿主派发同一时刻的多个事件时，逐条推进可见前缀，不能让第一个 OnEvent 看见尚未派发的后续事件。

- 保留公共 `TimelineHistory` 构造函数对非法时刻、顺序、重复身份和来源的严格检查。宿主使用受控内部构造路径复用已验证表，不把“可信输入”开关暴露给脚本作者。
- 查询函数只访问可见前缀，按索引查找；已交付给作者的历史快照不随宿主继续推进而增长。未来端点查询仍走现有独立协议，不能通过底层表泄露未来记录。
- 公开 `Records` 目前返回 `ImmutableArray<EventRecord>`，不直接改成另一集合类型。建议保留签名，显式访问时才物化对应前缀并在该快照内缓存；宿主正常推进和内置查询不访问该兼容投影。
- 保留 120Hz 网格、精确事件时间、同刻顺序、OnEvent／Advance／Evaluate 及六阶段语义。反向跳转、取消后重建、输出模式变化都重新建立正确代次。
- 先处理历史复制；独立端点重放与既有 bridge 缓存另测命中和首次查询成本。本轮不顺带引入检查点或改写粒子确定性模型。

**验收：** 空效果不查询 `Records` 时，全量记录验证次数与事件数线性相关，边界推进没有完整前缀数组复制；公共构造的非法输入仍全部拒绝。覆盖同刻事件逐步可见、保留旧 History、取消后重放、24／30／60fps、普通／透明同帧及端点过去／未来边界。对显式每帧读取完整 `Records` 的作者单独记录仍需物化的成本，不虚报为全路径线性。

F7a已按ADR-0175在0.45.5实施；一次校验的代次事件表、只读可见前缀及按需兼容数组合同见[历史前缀](../../scripting-history-prefix-contract.md)。前后各36个10／30／180秒样本、独立过去／未来端点与桥接首次／命中计量、真实双输出编码及变异证据见修复验收／roadmap §18.148。显式Records数组物化及F7b诊断重复消费成本仍如实保留。

### F7b：诊断结构共享与增量消费

**推荐保留现有完整诊断的可观测语义，通过新宿主读取路径消除热路径复制。** 当前每帧的累积诊断不能简单清空，否则跳到较晚时刻的输出会漏掉中间 OnEvent／Advance 等阶段报告。

- 将实际语义阶段产生的诊断写入有代次和顺序号的追加日志，以不可变分块／持久结构形成快照；每份准备帧引用截止本边界的稳定快照，并保存本次分数时刻求值及绘制阶段自己的诊断。
- 现有 `PreparedRenderFrame.Diagnostics`／`RenderFrame.SceneDiagnostics` 的完整数组视图作为按需物化的兼容入口，保留内容和发生顺序。正式预览、导出和运行验证改用快照／增量枚举接口，不再逐帧读取完整兼容数组。
- 消费者使用代次与序号读取未消费的实际发生记录；缓存命中和同一语义边界的重用不再重复消费同一条记录。作者在不同调用中主动报告相同 Warning 仍是不同发生，不能按消息文本在采集层去重。
- 分数时刻请求产生的临时求值诊断与共享边界日志分开；跳转重建、预览缓存命中、从中途开始导出都必须获得应有的完整记录。缓存持有不可变诊断快照，释放原运行会话后仍可安全读取。
- Error 立即保留原有失败门禁，包括作者捕获 Error 的情况；包／修订／实例／阶段／时刻／源码位置不丢失。导出最终提示继续按既有规则汇总去重。
- 第一阶段把保留成本控制为实际诊断数 O(D)，消除每帧 O(D) 的复制与扫描；UI 只显示分页或汇总，但完整记录仍可取得。不得设置静默截断数量。若基准证明单个合法长会话的线性日志仍不可接受，再单独提出磁盘分段或明确预算合同，不在本批擅自让 Warning 导致失败。

这需要对现有“预览缓存保留完整数组”的实现描述作补充：缓存保留完整、稳定的诊断语义和按需数组投影。实施时更新诊断合同与宿主接口版本说明；不改变作者 SDK 的报告入口或静默删除真实报告。

**验收：** 旧探针的 0／1／2／5 秒完整诊断视图仍能取得 1／121／241／601 条报告，但正式消费者累计访问的共享日志条数不随帧数重复放大。增加所有作者阶段、同文不同来源、同帧多次报告、分数时刻、重复请求、缓存、跳转／取消、首次请求直接到远时刻和会话释放后读取。实测分配曲线和诊断复制／访问计数一起作为出口。
